## 二、各技术栈深度分析

### 2.1 FastAPI — ★★★★☆ 深入

**你用了什么：**
- 依赖注入（`Depends`）贯穿认证、数据库会话、权限校验
- 异步路由（`async def` 端点，全链路 `await`）
- 中间件（错误处理中间件、CORS）
- 自动生成 OpenAPI 文档（`/docs`、`/redoc`）
- 应用工厂模式（`create_app()`）
- `StreamingResponse` 实现 SSE
- 自定义异常处理器（422 校验错误）

**面试官会问：**

> **Q1: 你用了 `@app.on_event("startup")` 做初始化，但这个 API 在 FastAPI 0.100+ 已被标记为 deprecated，你知道现在推荐的方式吗？**

现状：项目使用的是已废弃的事件钩子。推荐方式是 `lifespan` 上下文管理器。这说明你对 FastAPI 版本演进的跟进不够。

> **Q2: 你的 `get_async_db()` 里 try/except 中 commit 了，但如果业务层已经手动 commit 了呢？会不会重复 commit？**

现状：`get_async_db()` 在正常退出时 auto-commit，但你的 service 层有些地方也手动 commit，存在双重 commit 的风险。这表明事务边界管理不够清晰。

> **Q3: 你的 CORS 配置是 `allow_methods=["*"]`、`allow_headers=["*"]`，这在生产环境有什么安全隐患？**

现状：通配符 CORS 在开发阶段没问题，但你的项目声称支持 Docker 生产部署，却没有区分环境的 CORS 策略。

**客观评价：** FastAPI 的核心特性你用到了 70%+，异步链路、依赖注入、中间件都有实践。但对框架版本演进和生产级细节（事务边界、CORS 收紧）关注不足。面试能聊，但要准备好被追问细节。

### 2.2 SQLAlchemy 2.0 (Async) — ★★★★☆ 深入

**你用了什么：**
- 异步引擎 `create_async_engine` + `async_sessionmaker`
- 连接池配置（`pool_size`、`max_overflow`、`pool_recycle`、`pool_pre_ping`）
- ORM 模型定义（18 张表，含自引用关系、复合索引）
- `selectinload` 预加载解决 N+1 问题
- 关系映射（`relationship` + `backref`）
- 异步查询（`select()` + `await session.execute()`）

**面试官会问：**

> **Q1: 你的 User 模型有 8 个单列索引，这合理吗？索引不是越多越好，你评估过写入性能影响吗？**

现状：`user` 表有 `idx_user_create_at`、`idx_user_update_at`、`idx_user_school_id`、`idx_user_student_id`、`idx_user_employee_id`、`idx_user_status`、`idx_user_email`、`idx_user_role`、`idx_user_enrollment_year` 共 9 个索引。对于一张用户表来说，这意味着每次 INSERT/UPDATE 都要维护 9 棵 B+ 树。`status`、`role` 这种低基数字段的单列索引在实际查询中可能根本不会被优化器选择。

> **Q2: 你同时维护了 `database.py`（同步）和 `database_async.py`（异步），为什么不统一？**

现状：两套数据库引擎并存，增加了维护成本。实际路由全部是异步的，同步引擎可能只是历史遗留。

> **Q3: `expire_on_commit=False` 你知道它的副作用吗？**

现状：关闭 expire_on_commit 意味着 commit 后对象属性不会自动失效，可能读到过期数据。你选择这个配置是为了避免懒加载失败，但在并发场景下可能产生数据不一致。

**客观评价：** ORM 使用扎实，异步、预加载、连接池配置都有考虑。模型设计合理（层级组织、权限关联），但索引策略和双引擎并存暴露了经验不足。

### 2.3 ReAct Agent 引擎 — ★★★★☆ 深入（核心亮点）

**你实现了什么：**
- ReAct (Reasoning + Acting) 循环：LLM 决策 → 工具调用 → 结果反馈 → 再决策
- 5 种工具：知识库检索、数据库查询、计算器、时间工具、话题分析
- 动态工具注册（按用户消息语义按需加载，减少 token 开销）
- 状态机编排（IDLE → PLANNING → TOOL_CALLING → REFLECTING → RESPONDING → DONE）
- Trace/Span 追踪（记录每步的输入、输出、延迟、token 消耗）
- 最大迭代次数兜底（5 轮）

**面试官会问：**

> **Q1: 你的 Agent 最终回答阶段不是流式的。你获取完整响应后用 `CHUNK_SIZE = 4` 逐字符模拟打字效果，为什么不直接用 `stream=True`？**

```python
# engine.py:204-208 — 这是假流式
CHUNK_SIZE = 4
for i in range(0, len(accumulated_content), CHUNK_SIZE):
    chunk = accumulated_content[i:i + CHUNK_SIZE]
    yield AgentEvent(type="token", data={"content": chunk})
```

现状：中间决策轮次用 `stream=False` 是合理的（减少开销），但最终回答也用非流式，然后假装流式输出，用户实际感受是"等半天然后突然全部出来"，而不是逐 token 流出。`SimpleStreamEngine` 反而是真流式（`stream=True`），形成了不一致。

> **Q2: 你的 CalculatorTool 使用了 `eval()`，即使你限制了 `__builtins__`，这仍然有安全风险。你知道为什么吗？**

```python
# tools.py:186 — eval 是危险的
result = eval(cleaned, {"__builtins__": {}}, self.SAFE_FUNCTIONS)
```

现状：`eval` 即使限制了 builtins，也可能通过 `().__class__.__bases__[0].__subclasses__()` 等方式逃逸。安全的做法是用 `ast.literal_eval` 或自己写一个表达式解析器。面试中这会被直接追问。

> **Q3: 你的 TopicAnalysisTool 是纯关键词匹配的规则引擎，为什么叫"Tool"让 LLM 来调用？LLM 调用一个关键词匹配函数有什么意义？**

现状：`TopicAnalysisTool` 本质上是一个 `if keyword in message` 的映射表，让 LLM 花一次 API 调用来触发它，不如直接在路由层做。这暴露了对 Agent 工具设计的理解不够深——工具应该是 LLM 自身无法完成的操作（数据库查询、API 调用、计算），而不是 LLM 本身就能做的文本分类。

> **Q4: 多工具并行调用你支持吗？**

现状：当 LLM 返回多个 `tool_calls` 时，你是用 `for tc in message.tool_calls` 串行执行的。如果有 3 个工具调用，每个耗时 1 秒，总耗时 3 秒而不是 1 秒。应该用 `asyncio.gather` 并发执行。

**客观评价：** ReAct 模式实现完整，状态机 + Trace 追踪是亮点。但假流式、eval 安全隐患、串行工具执行、TopicAnalysisTool 设计不合理是明显的短板。面试时作为核心项目亮点来聊是可以的，但要准备好上述追问。

### 2.4 混合检索 + RRF 融合 — ★★★★☆ 深入（核心亮点）

**你实现了什么：**
- 向量检索（ChromaDB）+ BM25 关键词检索
- Reciprocal Rank Fusion (RRF) 算法融合两路结果
- 距离函数自动检测（cosine / L2 / IP）+ 统一相似度映射
- BM25 索引 LRU 缓存（20 个槽位，10 分钟 TTL）
- jieba 中文分词 + 停用词过滤
- 优雅降级（jieba 不可用时降级为字符 bigram）
- 按文档去重（同一文档多个 chunk 只保留最高分）
- 向量检索和 BM25 检索并发执行（`asyncio.gather`）

**面试官会问：**

> **Q1: RRF 的 k=60 这个参数是怎么来的？你做过调参实验吗？**

现状：k=60 是 RRF 论文的默认值，直接使用没问题，但如果面试官问你为什么是 60 而不是 50 或 100，你需要理解 k 控制的是低排名结果的惩罚程度。

> **Q2: 你的 alpha 参数默认 0.7（向量权重 70%），这个值是怎么确定的？不同场景下应该怎么调？**

现状：alpha 是硬编码的，没有根据查询特征动态调整。比如短关键词查询可能 BM25 更好（alpha 偏低），长语义查询向量更好（alpha 偏高）。

> **Q3: BM25 缓存在进程内存中，多 worker 进程部署时每个进程各维护一份缓存，你考虑过吗？**

现状：缓存用的是模块级全局变量 `_BM25_CACHE`，Uvicorn 多 worker 模式下每个进程独立缓存，内存翻倍且缓存命中率下降。

**客观评价：** 这是项目中技术含量最高的模块之一。RRF 融合、LRU 缓存、降级策略、并发检索都实现得不错。面试重点推荐聊这个模块。

### 2.5 层级 RBAC 权限系统 — ★★★★☆ 深入（核心亮点）

**你实现了什么：**
- 5 层组织架构（学校 → 学院 → 专业 → 班级）自引用树
- 角色-权限-用户三层关联
- 权限继承：子组织自动继承父组织权限
- 前端路由守卫 + 后端依赖注入双重校验
- 权限检查结果缓存（TTL 5 分钟）
- `require_permission` 装饰器
- `require_organization_access` 组织级访问控制

**面试官会问：**

> **Q1: 你的权限检查每次都要沿着组织路径向上遍历，最坏情况是 O(depth) 次数据库查询。你做了缓存，但 TTL 5 分钟意味着角色变更后用户可能在 5 分钟内仍有旧权限。怎么解决？**

现状：缓存失效策略是被动过期（TTL），没有主动失效机制。角色变更后应该清除相关缓存。

> **Q2: 前端路由守卫中检查权限用的是 `userStore.hasPermission()`，这个方法是调 API 还是读本地缓存？如果用户在另一个 tab 被管理员移除了权限呢？**

现状：前端的权限数据是登录时加载的，之后没有刷新机制。理论上存在权限过期的窗口。

> **Q3: 你同时有 `user.role` 字段（admin/teacher/student）和 RBAC 角色表，两套体系并存不矛盾吗？**

现状：`auth.py:158-168` 中有一段兼容代码，把 `user.role` 字段映射成 RBAC 角色代码。这说明你在从简单角色模型向 RBAC 迁移，但迁移不彻底，两套体系并存增加了复杂度。

**客观评价：** 权限系统设计完整度很高，层级继承 + 组织作用域是真正有深度的设计。但双体系并存和缓存一致性是短板。

### 2.6 SSE 流式协议 — ★★★★☆ 深入（核心亮点）

**你实现了什么：**
- 后端：自定义 SSE 事件协议（10+ 种事件类型：token、state_change、thinking、tool_call、tool_result、sources、metadata、memory、trace、done、error）
- 前端：基于 `fetch + ReadableStream` 的 SSE 客户端（不是 EventSource）
- 类型安全的回调分发（`StreamCallbacks` 接口）
- AbortController 支持中断生成
- SSE 事件缓冲区正确处理不完整的帧

**面试官会问：**

> **Q1: 你为什么不用浏览器原生的 `EventSource` API，而是用 fetch + ReadableStream 自己解析？**

这是一个好的设计决策。`EventSource` 只支持 GET 请求且无法设置 Authorization header，你的场景需要 POST + Bearer Token，所以手动实现是正确的。这个回答能加分。

> **Q2: 如果网络中断，你的 SSE 连接有重连机制吗？**

现状：没有。`fetch` 请求一旦断开不会自动重连，前端只处理了 `done` 和 `error` 事件。

**客观评价：** SSE 协议设计得相当专业，事件类型丰富，前后端配合完整。这是面试时可以展示系统设计能力的模块。

## 三、架构设计评审

### 3.1 后端分层架构

```
Router → Service → Mapper → Model
```

**优点：**
- 分层清晰，职责分明
- Mapper 层封装了数据访问，易于测试
- Service 层集中业务逻辑

**问题：**
- Mapper 层和 SQLAlchemy 的 Repository 模式重复——SQLAlchemy 的 Session 本身就是 UoW + Repository，Mapper 层的价值有限
- Service 层文件过大（`vector_service.py` 80KB+，`chat_service.py` 46KB+），需要拆分

### 3.2 Agent 架构

```
意图路由 → Agent 引擎（ReAct 循环）→ 工具调用 → 状态机 → Trace 追踪
       ↘ 简单流式引擎（无工具）
```

**优点：**
- 意图分类零 LLM 调用，节省成本
- 双引擎设计（Agent 模式 / 简单流式）符合实际需求
- 状态机保证状态转换合法性

**问题：**
- 意图分类是硬编码正则，不可扩展
- Agent 模式的最终回答是假流式
- 没有工具执行超时机制
- 没有工具执行失败重试机制

### 3.3 RAG 管线

```
文档上传 → 格式解析 → 文本分块 → Embedding → ChromaDB 入库
查询 → 向量检索 ∥ BM25 检索 → RRF 融合 → 去重 → 返回
```

**优点：**
- 完整的端到端 RAG 实现，不依赖框架
- 三种分块策略可选
- 混合检索 + RRF 融合提升召回率
- 降级机制完善（BM25 不可用时退化为纯向量）

**问题：**
- 没有 Re-ranking 步骤（检索后排序）
- Embedding 模型硬编码为阿里云 DashScope，切换模型需要改配置
- 没有文档更新后的增量索引机制
- 分块策略是全局配置而非按文档类型自动选择
