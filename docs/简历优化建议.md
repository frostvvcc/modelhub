## 二、优先级排序：先做什么最能提升简历

### P0 — 必须做（没有这些，Agent 岗位简历直接不过筛）

#### 1. 加入流式输出（SSE）— 预计 2-3 天

这是最基础的要求。你的 chat_service.py 目前是等 LLM 完整回复后一次性返回的，任何做过 LLM 应用的面试官一眼就能看出来。

**具体做法：**
- 后端：FastAPI `StreamingResponse` + `async yield`，把 LLM 的 token 逐个 yield 出去
- 前端：`EventSource` 或 `fetch` + `ReadableStream`，实现打字机效果
- 对话过程中显示"思考中..."，token 到达后逐字渲染

**简历写法：**
> 基于 SSE 实现流式对话，前端通过 ReadableStream 逐 token 渲染，首 token 延迟 < 500ms

#### 2. 实现 Tool Calling + Agent 循环 — 预计 4-5 天

这是你简历上"Agent 开发"四个字能否成立的关键。**不需要接入 LangChain**，自研反而是加分项。

**具体做法：**
```
推荐自研一个轻量 Agent 框架：

1. 定义 Tool 接口：
   - 知识库检索工具（已有，包装一下）
   - 数据库查询工具（查询学校信息、课程信息等）
   - 计算器工具
   - 网页摘要工具（可选）

2. 实现 ReAct 循环：
   用户消息 → LLM 判断是否需要调用工具
   → 需要：解析 tool_call，执行工具，把结果喂回 LLM
   → 不需要：直接回复
   → 循环直到 LLM 给出最终回答（设最大轮次兜底）

3. 用 OpenAI 兼容的 Function Calling 协议：
   在请求里带 tools 参数，解析 response 里的 tool_calls
```

**简历写法：**
> 自研轻量 Agent 引擎，基于 ReAct 模式实现多轮工具调用，支持知识库检索、数据查询等 5 种工具，平均 1.8 轮完成复杂任务

#### 3. Agent 编排 — 在 Tool Calling 基础上加 2-3 天

有了 Tool Calling，再往上做一层编排。

**具体做法：**
```
方案 A（推荐 — 自研状态机）：
  定义 Agent 的状态流转：
  IDLE → PLANNING → TOOL_CALLING → REFLECTING → RESPONDING → DONE
  每个状态有明确的进入/退出条件
  支持多 Agent 协作（如：一个 Agent 做检索，一个 Agent 做总结）

方案 B（如果时间紧 — 用 LangGraph）：
  pip install langgraph
  定义 StateGraph，节点是你的各个工具和判断逻辑
  好处：面试时可以画出 Graph 结构
```

**简历写法（方案 A）：**
> 设计并实现基于有限状态机的 Agent 编排引擎，支持多 Agent 协作和工具链路追踪

**简历写法（方案 B）：**
> 基于 LangGraph 构建多步骤 Agent 工作流，实现检索-分析-总结的自动化流程

### P1 — 强烈建议做（面试深入追问时的加分项）

#### 4. LLM 可观测性 — 预计 1-2 天

面试官常问："你怎么调试 LLM 应用？怎么知道哪一步出了问题？"

**具体做法：**
- 每次 Agent 调用链记录完整 Trace：用户输入 → 意图识别 → 工具调用（参数+返回值）→ LLM 推理 → 最终输出
- 存入数据库或日志，前端可视化展示调用链路
- 记录每步的 token 消耗、延迟、相似度分数

**不需要上 OpenTelemetry，自己写一个简单的 TraceContext 就行：**
```python
class TraceContext:
    trace_id: str
    spans: List[Span]  # 每个 Span 记录一步操作

class Span:
    name: str           # "tool_call:knowledge_search"
    input: dict
    output: dict
    latency_ms: int
    tokens_used: int
```

**简历写法：**
> 设计 Agent 调用链追踪系统，记录完整的 Trace/Span 信息，支持可视化回放和性能分析

#### 5. 前端对话体验升级 — 预计 2-3 天

目前前端只是基础的消息列表。做 LLM 产品的公司对交互体验要求很高。

**需要加的：**
- 流式 Markdown 渲染（token 到一个渲染一个，不是全部到了再渲染）
- Agent 思考过程可视化（展示"正在检索知识库..."、"正在调用XX工具..."）
- 引用来源可点击展开原文
- 代码块语法高亮 + 一键复制
- 对话分支（可选，加分大）

**简历写法：**
> 实现流式 Markdown 渲染引擎，支持 Agent 推理过程实时可视化和引用溯源交互

#### 6. 多轮对话记忆管理 — 预计 1-2 天

你当前的 context window 管理很原始（取最近 N 条消息）。

**升级方向：**
- 实现对话摘要压缩：超过 N 轮时，用 LLM 总结前面的对话再拼接
- Token 计数：用 tiktoken 精确计算，而不是靠消息条数
- 滑动窗口 + 摘要混合策略

**简历写法：**
> 实现基于 token 计数的对话记忆管理，支持滑动窗口 + 自动摘要压缩，在 4K context 下维持 20+ 轮连贯对话

## 六、关键提醒

1. **自研 > 套框架**：面试时"我自己实现了一个轻量 Agent 引擎"比"我用了 LangChain"有说服力得多。LangChain 谁都能 pip install，但理解 ReAct 循环的人不多。

2. **数字 > 形容词**：简历上"提升了性能"不如"P99 延迟从 2s 降到 400ms"。每个优化点都要有数据支撑。

3. **能画图 > 能说话**：面试时能画出 Agent 的状态流转图、RAG 的 Pipeline 图、系统架构图，比口述强 10 倍。准备好这三张图。

4. **深度 > 广度**：与其加 10 个浅功能，不如把 Agent + RAG + 流式输出这三个做深。面试官只会在你最有深度的点上追问。

5. **项目要能跑**：面试时如果能现场 Demo（哪怕是录屏），效果远超 PPT。确保 Docker Compose 一键启动、3 分钟能跑出完整流程。
