### 2.1 P0 — eval() 代码注入漏洞

**文件**: `backend/app/services/agent/tools.py`

**修复前（危险代码）**:
```python
result = eval(cleaned, {"__builtins__": {}}, self.SAFE_FUNCTIONS)
```

**修复后（安全代码）**:
```python
tree = ast.parse(cleaned, mode='eval')
result = self._safe_eval(tree)
```

**安全解析器实现原理**:
- 用 `ast.parse()` 将表达式解析为抽象语法树
- 递归遍历 AST 节点，仅允许以下节点类型：
  - `ast.Constant` — 数字字面量（int / float）
  - `ast.Name` — 白名单常量（`pi`, `e`）
  - `ast.BinOp` — 白名单二元运算（`+ - * / // % **`）
  - `ast.UnaryOp` — 一元运算（正负号）
  - `ast.Call` — 白名单函数调用（`sqrt`, `sin`, `cos`, `log` 等 15 个数学函数）
- **任何其他 AST 节点直接抛出 ValueError**

**不修复的后果**:
- `eval()` 即使限制了 `__builtins__`，仍可通过 `().__class__.__bases__[0].__subclasses__()` 等 Python 类方法链逃逸沙箱
- 攻击者可执行任意代码：读取服务器文件、获取环境变量（API Key）、反弹 Shell
- OWASP Top 10 之「代码注入」，面试官看到直接扣分

### 2.2 P0 — Agent 假流式 → 真流式

**文件**: `backend/app/services/agent/engine.py`（第 203-241 行）

**修复前（假流式）**:
```python
# 先拿完整响应，再 4 字符一组模拟打字
accumulated_content = message.content or ""
CHUNK_SIZE = 4
for i in range(0, len(accumulated_content), CHUNK_SIZE):
    chunk = accumulated_content[i:i + CHUNK_SIZE]
    yield AgentEvent(type="token", data={"content": chunk})
```

**修复后（真流式）**:
```python
# 用 stream=True 调用 LLM，逐 token yield
stream = await client.chat.completions.create(
    model=llm_client.model,
    messages=working_messages,
    stream=True,
)
async for chunk in stream:
    delta = chunk.choices[0].delta if chunk.choices else None
    if delta and delta.content:
        accumulated_content += delta.content
        yield AgentEvent(type="token", data={"content": delta.content})
```

**不修复的后果**:
- 用户体验：等 3-8 秒（LLM 完整生成），然后内容瞬间全部出现，不是逐字打字效果
- 首 token 延迟（TTFT）= LLM 生成全部内容的时间，而非第一个 token 的时间，体感差 5-10 倍
- 与同系统的 `SimpleStreamEngine`（真流式）形成自相矛盾
- 面试官一眼看出"这不是真流式"

### 2.4 P1 — 工具串行执行 → 并行执行

**文件**: `backend/app/services/agent/engine.py`

**修复前（串行）**:
```python
for tc in message.tool_calls:
    result = await tool.execute(**tool_args)  # 一个接一个等
```

**修复后（并行）**:
```python
# 所有工具同时执行
tool_results = await asyncio.gather(
    *[_exec_tool(tc, tn, ta) for tc, tn, ta in parsed_calls]
)
```

**不修复的后果**:
- 3 个工具各 1 秒：串行 = 3 秒，并行 = 1 秒，**3 倍性能差距**
- 简历写了"全链路 async/await"，却在核心模块串行执行——自相矛盾
- 面试官问"多工具并行你支持吗？"——代码里不支持就无法自圆其说

### 2.5 P1 — ChatView.vue 拆分为 Composables

**新建文件**:

| 文件 | 职责 | 行数 |
|------|------|------|
| `frontend/src/composables/useStreamChat.ts` | 流式对话：回调构建、停止/重新生成、空消息创建 | ~110 |
| `frontend/src/composables/useMarkdownRenderer.ts` | Markdown 渲染：代码高亮、引用 popover、节流刷新 | ~70 |
| `frontend/src/composables/useChatHelpers.ts` | UI 辅助：知识库选择、文件上传、来源/trace 面板 | ~170 |

**提取的逻辑映射**:

```
ChatView.vue (1272 行)
├── useStreamChat()        ← sendMessage 的回调构建、isGenerating、stopGenerating
├── useMarkdownRenderer()  ← renderMarkdown、引用点击、popover 定位
├── useChatHelpers()
│   ├── useKnowledgeBase() ← KB 选择、分组、加载
│   ├── useFileUpload()    ← 文件选择、去重、格式化
│   └── useChatUI()        ← 来源展开、trace 展开、复制、工具标签
└── 页面级逻辑（路由、会话管理）留在 ChatView.vue
```

**不修复的后果**:
- 1272 行单文件 = 无法维护、无法测试、无法复用
- BotChatView.vue（1337 行）有 70%+ 逻辑重复——改一处必须同步改两处，改漏就是 bug
- 面试官问"你的前端怎么组织？"—— 1272 行单文件违反组件化基本原则
